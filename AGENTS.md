# AGENTS.md

Durable, non-obvious knowledge for working in this repo. Facts recoverable
from the code or docs are not repeated here.

This file keeps the invariant and the reason: what a surface owes a rep, which
box is named when it fails, why a rule exists at all. The narrative behind each
section — the rule in full, the probe that proved it, the layout it was measured
on — lives in the `docs/` file that section names. Measured numbers have one
home, `reports/browser-readings.md`, generated by `npm run readings:freeze` from
a run of the browser walk; `reports/` is ignored like any other generated
output, so a checkout makes its own rather than inheriting one. A number quoted
in prose records the run that decided the rule, not a promise about today's
layout: re-read the report rather than trusting a figure copied into a sentence,
because a stale measurement reads exactly like a live one. Every surface note in
`docs/` links the report section carrying its numbers, and `npm run check:docs`
holds both halves of that index: a section no note claims is a reading nobody can
find, and a note pointing at a section the walk no longer prints is a link that
would quietly stop meaning anything.

Change both halves together. An invariant here with no narrative is a rule the
next reader cannot check; a narrative in `docs/` for a rule this file no longer
states is one they trust by mistake.



## Worktree & dev workflow

- File tools resolve paths from the thread worktree (`.freebuff/worktrees/<id>/`);
  main-checkout paths error as "file does not exist". Edit in the worktree,
  then `cp` changed files to the main checkout (`C:/Users/steve/wingman`) and
  keep both byte-identical. Copying main→worktree after an edit silently
  discards the edit — diff the two files after any sync. The file tool also
  resolves `/tmp/...` to `C:\tmp\` on this Windows setup.
- Git Bash `kill` cannot terminate Windows-native node processes: the old
  server survives, the new one hits EADDRINUSE, and curl keeps hitting the
  STALE code — verification silently passes against old behavior. Kill with
  `powershell -Command "Stop-Process -Id <pid> -Force"` and confirm the port
  freed via netstat.
- `npm run dev` (via `tools/start-wingman-dev.mjs`) starts BOTH the UI (3000)
  and the API (8787) and aborts entirely if 8787 is already bound. The
  competitor-lookup server (`server/competitor-lookup-server.mjs`) often holds
  8787 already — to serve just the UI run `node node_modules/vite/bin/vite.js`
  from the main checkout.
- The local dev sign-in is scripted: `npm run check:dev-pair-sync` attaches to a
  running pair, signs in through Settings → Workspace in a throwaway browser
  context and fails unless the Projects chip reads a synced workspace, so
  nothing is signed in on the developer's own browser. Loading any page seeds
  the starter examples into the legacy project store
  (`wingman-project-store-v1`), and that sign-in migrates the store into the
  new workspace scope. A sample is not an edit: `isUntouchedStarterExample`
  takes the workspace copy of a demo the browser has only ever held untouched
  sample text for, without a conflict, so a page-load stamp cannot outrank it;
  a sample someone renamed or put work into keeps the normal per-lane policy.
  `check:e2e-smoke` runs the check against the pair its harness boots, so the
  merge is gated on every PR; run the script alone only when debugging it
  against your own `npm run dev`.
- On Windows, start preview servers with the PowerShell `Start-Process`
  recipe and stdout/stderr to DIFFERENT log files. `register_preview` with
  `replace: true` stops the previously registered server first.
- When a preview screenshot fails with "produced no frames" or the webview
  detaches, DOM-level verification via `preview_evaluate` still works — use it
  as the fallback instead of assuming the page is broken.

## Project store

- `createProjectLifecycleCommands` returns the four ways a project is written,
  and what separates them is the promise each makes about the gallery order and
  about what the rep is reading. `replaceStoredProject` rewrites the row where
  it sits and leaves `activeProjectId` alone, so an approval arriving from the
  queue cannot take the rep off their own project. `upsertStoredProject` is the
  rep choosing the project, so the row goes to the front and becomes the
  reading — the one case where order and reading change together.
  `updateStoredProject` is an edit, so the row keeps its slot and becomes the
  reading; re-ranking the gallery on every edit is what a save does, not a
  change. `deleteStoredProject` closes the gap without re-ordering and clears
  the reading only when the deleted row was the one being read.
  `projectCommands.test.ts` pins all four: add a spec there rather than trusting
  a new caller to state which promise it keeps.
- `updateStoredProject` declares `StoredProject | null` and finds its row before
  replacing it through `map`, because TypeScript does not narrow a value
  assigned inside a callback: the old shape returned `null` to a caller that had
  just written the project.
- A stored record carries only fields a surface reads, and the codecs are
  allow-lists, so removing one needs no migration — an older document's value is
  simply not read back. Removing a field is right when nothing reads it; keeping
  it is right when the missing reader is a surface gap, which is why the CRM
  history's stored failure reason was given a line to print rather than deleted.
- The CRM send history is the record of what left the browser and what came
  back, and each row says what it can still do. A failed send keeps the exact
  body it POSTed and offers a retry that sends that snapshot verbatim to
  whatever endpoint is configured now, because the CRM should get the body the
  rep first tried rather than a rebuild of a room that moved on. A send that
  landed keeps no body, so only a failed row has the action.
- `sendHistoryEntry` is the one place a row is made from an outcome and
  `resendHistoryEntry` is its pair. A retry records its own entry and leaves the
  original failure alone, because that failure is the record of what went wrong
  first. A retry that fails again simply stores the body on its new row.
- `resendableProjectFailures` is the only place the question "which rows can be
  resent" is answered. The history is one list across every room, so the batch
  resends this project's failures and leaves another room's alone, and excludes
  a failure recorded before bodies were kept rather than queueing a guaranteed
  error; the note prints how many could not be retried, or those rows would keep
  reading as sends the batch missed. Retries run in order, not in parallel, so a
  refusal is attributed to the send that met it and one endpoint never receives
  the batch at once. One retrying id disables the row actions and the batch
  together, so the two cannot interleave.
- A retry that lands marks the row it came from, and that is the one row
  rewritten in place rather than appended: the body has been delivered, so the
  row stops offering its action and printing the body it no longer needs, while
  the failure, its reason and its time stay as the record of what happened. The
  delivered snapshot goes with the mark, because it can never be sent again and
  a body carrying the discovery brief is the largest thing a row holds.
- Boot cleans what an older build left. `sweepWebhookHistory`, called from
  `main.tsx`'s install block and pinned by `check:runtime-wiring`, clears
  delivered bodies and trims a history over its ceilings, and writes only when
  it changed something. Leaving that to "the next time the rep opens the CRM
  panel" means the reps who never open it keep the biggest rows forever. Both
  ceilings live in one function — count first, to pick the sends, then budget to
  fit them — so the write path and the sweep cannot obey different rules, and
  the newest row is never dropped, because it is the send the rep just made. A
  drop is reported once, browser-wide, and the note that prints it is mounted in
  both places a rep asks: above the send list, and above the project record's
  activity trail, since the browsers holding the biggest copies belong to the
  reps who never open the panel. One wording and one dismissal serve both.
- A write can still be refused, because the history shares the origin with the
  project store, so the record function returns whether the row was stored and
  the panel prints the loss instead of swallowing it. The two outcomes are said
  apart because they ask different things of the rep: a send the endpoint
  accepted has already gone, so the loss is that the list will not offer it
  again, while a send that failed has lost the only body a retry could post.
  Silence would read as a send that never happened.
- `Clear history` is the rep's way out of that state: it asks first, and both
  the confirmation and the note afterwards name how many kept bodies go, because
  they live nowhere else. Every row also carries its own drop action, which arms
  and confirms on the same button and prints what that row costs — the body a
  retry could post, or only this browser's record of a send the CRM already has.
  A dropped row is gone rather than marked, and that is what separates it from a
  resend: a delivered body is a finished attempt whose failure is still worth
  reading, while a dropped row is one the rep asked to be rid of. The list is
  re-read from the store after the write, so a refused rewrite leaves the row
  where a rep can see it is still recorded.
- The panel and its rows are grid and flex children, so each carries the minimum
  that stops a widest row deciding the column's width: `min-width: 0` on the
  panel, and below the row's breakpoint the row wraps with the project name on
  the first line and the status, time and controls below it. Wrapping at every
  width breaks rows that fit, and a name squeezed to its floor leaves a dot, a
  code and a time to tell one send from another.
- Deleting a store from the source does not delete it from a rep's browser, so
  the install block also runs `sweepRetiredStorage`, and `RETIRED_STORAGE_KEYS`
  is the whole record of what is retired: no shipped source names those keys any
  more, so the list is the only thing that could find them. Nothing is migrated,
  because nothing reads it. Waiting for a rep to open the surface that used to
  write the key is the failure the sweep exists to avoid; it touches only keys
  that are present and stays silent on a store the browser refuses.
- The sweep reports what it took back, but never on the load that takes it. Boot
  runs before any surface exists, so the size is left for the *next* load, whose
  take happens before its own sweep can add to it. That ordering is the whole
  mechanism: a load can only report space a previous load reclaimed, so the
  number prints once. The report is shared with the CRM cleanup, because a rep
  asking whether space came back is asking about their browser rather than about
  one store, and each share is measured in the browser's own units from the two
  documents so the total is never a sum of different things. The wording has a
  sentence per source because the two cannot promise the same thing: a retired
  copy is read by nothing, so nothing a project holds went missing, while the
  history cleanup gives up delivered copies and the oldest sends, which the
  panel names.
- The store's sync line reads a teammate's change exactly the way the gallery
  cards do: one helper folds the lanes and one wraps them for the line, and the
  card's badge calls the same helper, so the two readings cannot drift into
  saying one change two ways. The line takes its rooms off the stored conflict
  flags rather than the sync status, because the badges it sits above are stored
  facts: a session that ended still holds both, and the line above a badged card
  cannot go quiet while the card speaks. That is also what lets the browser walk
  hold it, since the walk builds with sync off.
- The saved design under a card is the one cell whose payload is a design's
  name, so it keeps a floor at every width a column could squeeze it, and the
  guided strip's saved-design link carries the same rule. The number is one
  shared floor with one failure sentence, because a floor per surface let the
  gallery allow a stub the strip would have failed; it is a stub guard, not a
  target either surface is measured against, and it is 20 because a card's
  two-column line keeps more of a long name than that — while the phone and the
  single-column band print the name whole, because below 761px the label takes a
  second line. A name that only fits on one line is a reading of the typeface as
  much as of the card, which is why the family is delivered rather than merely
  named: with a fallback sans the runner printed 17 where the developer's machine
  printed 23 in the same entry and the floor failed on a branch where nothing
  about the card had changed. What each width actually kept is
  read off `designNameWidthClause` in `tools/lib/saved-design-names.mjs`: the
  longest-named entry, its card, and the runner-up beside it, which is what
  separates a column's budget from one card's own width. The numbers a floor is
  argued from come from that sentence and the frozen report, never from a copy
  of them in prose.
- That separation is a claim the walk makes, so it is checked rather than assumed:
  the pick and its runner-up have to have been given one column, and the walk fails
  in `designNameWidthAgreementFailure` when the two entry boxes are further apart
  than a character of the pick's own text. Not the printed counts — two different
  names never print the same count, because the same 359px entry held 40
  characters of a 101-character name and 45 of a 92-character one at 1366px, so
  comparing counts would fail every width for typography rather than for layout.
  Compare the boxes. A runner-up whose name printed whole gets no comparing: its
  link ends where the name ends, so that cell is its own name's width rather than
  the column's, and the width keeps the pick's count alone.
- The browser walk (`tools/browser-smoke-check.mjs`) holds these surfaces in a
  real browser. Every pick that decides *which* seeded thing is measured asks by
  content — the widest row, the short-named send, the card by its room label,
  the design entry with the most name to lose — because a positional pick
  measures whatever the seed put first and reads as the same claim when it is a
  different row. The indices that survive index the walk's own seed constants.

## Typecheck, tests and chunk init order

- Tailwind v4 runs through `@tailwindcss/vite`; keep Vite's inline empty PostCSS
  configuration, or a nested worktree discovers an ancestor's untracked
  `postcss.config.js` holding the retired v3 plugin. API and HTML can answer
  while CSS compilation fails, so the dev-pair health check must fetch the
  layout CSS route with `?direct`.
- Capture-region ids are `discovery-<region>` and actions are
  `discovery-<verb>-<object>`; repeated choices append stable model ids, never
  display labels, because the walk drives those ids and a label change would
  silently retarget it. Copy assertions belong in content tests.
- `tsc --noEmit` on the default config only checks the import closure of
  `src/main.tsx`, so it is a false green; the gate is
  `npx tsc --noEmit -p tsconfig.typecheck.json`. The two configs must agree
  about `noImplicitAny`, because the editor reads one and CI the other: the gate
  once carried a waiver that hid errors the editor showed. Do not put the waiver
  back to silence a new error — those errors were one untyped bag, and a read
  from a bag stays unchecked until someone names a type at the use site.
- Server tests import `@vitest/runner` and must run under `npx vitest run`;
  `node --test` fails with a harness error that reads like a test failure. To
  exercise authenticated API branches, boot the API from the worktree on a test
  PORT, so the file-mode store writes only to the worktree's ignored runtime
  directory, and reuse a throwaway workspace's session cookie.
- `check:init-order` asks the bundler whether a page load can run a
  module-scope read before the chunk it takes from. It builds in memory with the
  shipped chunk groups and reads the emitted chunks, because a statement the
  bundler dropped cannot fail and a source-level model of the bundler reported
  reads that no longer existed. Only a function declaration is initialized
  before any chunk body runs: `var` is `undefined` and `let`/`const`/`class` sit
  in the temporal dead zone, which is the difference between a working app and a
  false alarm. A binding the scan cannot find counts as uninitialized, so the
  gate fails closed.
- The question is asked once per entry load — the app's boot plus every dynamic
  entry chunk — because the same cycle is safe or fatal depending on where it is
  entered: the reader is only in trouble when the entry reaches it *through* the
  definer.
- The gate rests on `includeDependenciesRecursively: false`: with the dependency
  walk on, one chunk group takes another's whole closure and these cycles mostly
  cannot form, so a reordering that stops reporting anything is worth a look
  before it is believed. The tool has two failure modes whose symptom is a green
  run — a source file read without parent nodes, and a child visitor that
  swallows an exception.
- Build-stage gates are guarded from outside their stage, because that is the
  class of gate that goes quiet without failing: one contract check holds a list
  of the gates the build stage is trusted for and fails when one leaves
  `package.json`, stops being reachable from the stage, or drops out of the CI
  job. A self-check inside the stage disappears with the line it protects. Each
  entry carries the question its gate asks, so a failure names the question that
  stopped being asked.

## Quality gates and ratchets

- The stage guard exists because one CI job is where most wiring guards run:
  deleting it, or dropping a stage from its matrix, silences all of them at once
  and no guard inside them can report it, because their runners leave with the
  job. The strict-chain guard pins the strict twins against the stages they
  replace, and the coverage guard asks the next question — whether anything runs
  the scripts that exist at all — then asks it one level down, because a script
  can be wired to a stage and still call a file nothing else names. A tool under
  `tools/` that no script, workflow or import reaches is declared in
  `tools/tool-reach-exemptions.json` with what it is instead: a writer that ran
  once, a report, a companion to a gate. A gate is not a declaration — it goes in
  the stage that owns its question, and the stage's list is where that decision is
  read from — because a gate nothing runs reports nothing and its silence reads
  exactly like a pass. The reading counts an import position rather than a mention
  — a failure sentence naming the tool that fixes it is prose, not a caller — and a
  spec naming a tool is the guard's subject rather than its caller, so a helper its
  own spec imports is declared as one.
- The pre-commit hook runs the dead-CSS autofix and gate, then the fast lane and
  architecture boundaries; the full chain adds the two debt ratchets, size
  budgets and style drift. A ratchet with no baseline is a gate that fails on
  the repo it ships with.
- Size budgets sum every emitted chunk, on-demand libraries included: each has a
  job, and a byte hunt should start from a reading rather than from the total.
- The style-drift baseline counts page-scoped rule blocks, so it is raised
  deliberately, one rule at a time, and never as a target.
- The dead-CSS gate fails both ways — an unmatchable selector that is not
  baselined, and a baselined selector that is no longer dead — so the file only
  ratchets down. Detection is shared with the consolidation tool, because two
  implementations of "dead" is one more than a gate can hold.
- The autofix only splits a mixed selector list, copying live declarations byte
  for byte; a rule whose every branch is dead is left for a person, because
  removing it deletes styling. Fully dead rules become a reviewable patch rather
  than a silent edit, and applying the patch is a separate command.
- Deadness is structural: a rule is dead when every comma branch has a compound
  whose classes are all unused, so an ancestor-only orphan is caught. A class
  family counts as runtime-assembled only when source actually builds a class
  with it — a declaration or function named for classes is assembly, a string in
  passing prose is not.
- The unstyled-classes gate is the inverse: markup naming no stylesheet fails
  unless baselined, and `<style>` blocks inside export builders count as
  stylesheets, because the generated document's own sheet is one.
- A page does not import its own stylesheet, and the files that may are a list in
  one module: `GOVERNED_CSS_IMPORT_SITES` in `tools/lib/route-stylesheets.mjs`,
  read by the CSS-import guard and by the page-density report. Two copies of that
  list is how they stopped agreeing — the report's copy lacked the two reviewed
  entries, so it failed on an import the guard allowed, which leaves a report a
  person cannot run rather than a stricter gate.
- A route stylesheet's move is answered by the equivalence lib rather than by a
  byte diff: the split gate reads each page's own file against the rules the
  shared remainder still holds for that page, and a run has to come back proven
  or with a ranked list whose pairs a person has pinned. The baseline carries one
  reviewed decision per page and the pairs beneath it, and fails both ways — an
  unreviewed pair, and a pinned pair that stopped occurring — so the split can
  only ever re-decide what was read. Both sides are that page's own route scope,
  which is the population the split moved; a page rule against a shared rule no
  route scopes is a different question, and the summary names it rather than
  letting a green run imply it.
- A pair whose two subjects share no token is settled by the page rather than
  reviewed as a decision: the settle tool asks each route's DOM at two widths
  whether any element matches both selectors, and the baseline keeps what it
  proves cannot meet in a per-page `settled` list with the measurement beside it.
  The CSS gate only holds the bookkeeping — a settled pair cannot also be pinned,
  a settlement needs its evidence line, a settled entry cannot go stale — because
  it cannot open a page. The tool is the re-proof, and the browser walk asks the
  same question on every run through the same lib, so a page that starts
  mounting a settled pair is named in the walk that measured it rather than
  waiting for the next CSS change to call it unreviewed. The walk also names a
  pair nobody has answered for at all, and says which answer it is: one element
  matching both is a decision the baseline owes in `pairs`, none matching is a
  reading the tool should write.
- Route scope has two vocabularies, not one fact written twice:
  `html[data-wingman-route="<key>"]` takes the catalogue keys and
  `.wm-route-<segment>` takes the manifest segments, and 14 of 29 routes differ,
  so a kebab-cased segment is never an attribute value and a camelCase key is
  never a class. Both live sets are read from their writers — the union, the
  manifest, and the admin literal the shell sets in both spellings — never from
  a list that merely looks like the right shape, because a union of the two is
  how `data-wingman-route="call-coach"` would count as live while matching
  nothing. `check:route-scope-liveness` fails on a scope naming a value nothing
  writes, which no other reading can see (the class family is assembled at
  runtime, an attribute is not a class), and the prune tool asks the same lib so
  the two cannot disagree. Its baseline pins each dead value by count and by the
  story that left it; it ratchets down, and adding a value is a decision about
  dead styling rather than a way past a red run. It lists nothing today: the
  visual-studio route and the planner-era class scopes it pinned were deleted,
  and the baseline came down to match.
- Coverage and triage reports are the evidence side of the same question, and an
  unmatched rule is only evidence, never permission: a selector that needs a
  state the sweep never enters (expanded, dialog, drag, print) is unmatched but
  live. Prune only when every class token is also absent from the app's own
  non-test source, and keep any rule a tool or a spec renders.
- Export validation domains are held to tests that read the domain from the
  runtime list, so a new domain cannot arrive unproven, and the fixture SKU gate
  asks the lifecycle question about the fixtures proposals are tested against.
- The PR-description check reads GitHub, which is why it is its own workflow
  rather than a verify stage: a present-tense failure claim goes stale the
  moment the checks on the head go green.
- The sales-facing-language check scans all source, test and CSS comments
  included — developer wording about what changed is not for a rep.
- A competitor catalogue row ages on the same evidence clock as a confirmed
  WyreStorm profile, and both limits are read from
  `data/governance/profile-confirmation-aging.json` rather than restated in the
  gate: two files holding one age is how the catalogue and the profile drift
  into disagreeing about what current means. The gate fails per row over the
  limit and names the source CSV, warns as one count rather than a line per row,
  and its baseline ratchets four ways — unpinned over the limit, a pin the
  catalogue dropped, a pin that came back inside the clock, a pin whose date
  disagrees with the row — because a waiver list that only grows is the backlog
  with a filename. [Narrative](docs/QUALITY_GATES.md)
- `npm run build` compiles tracked public assets without repairing source
  evidence; catalogue regeneration is explicit, and the ratchets only fire
  inside the verify stages. [Narrative](docs/QUALITY_GATES.md)

## Shell and page frame

- The workspace is a grid with an auto header row and a `minmax(0, 1fr)` body,
  so the header is the real header and can wrap taller than the topbar variable
  says. Sizing the main column from that variable makes the column overflow, and
  the page scrolls inside the layout instead of under the header.
- A page frame is one scrollbar narrower than its host on every route, and that
  is the stable scrollbar gutter reserving it so the layout does not jump
  between a short page and a scrolling one. Do not "fix" the right gutter.
- A hero template belongs in one shared place. The hero is a two-column grid, so
  a header written with three children puts the action row in the icon column;
  the shared rule gives that row a column above the breakpoint and a line of its
  own below it, with an `!important` companion beside the reference layer's
  template because an important rule can only be outranked by another. A page
  owns its row's internals but not the hero's shape.
- The topbar names the page twice — the route's label and its one-line summary —
  and both are read from the route catalogue rather than written per page. The
  summary is the half that goes missing without a failure: its styling stays,
  because the rules are shared with other selectors, and the route's purpose ends
  up reachable only by hovering the title. The page-style gate holds both markers
  for that reason, so a shell edit that drops one is a red run rather than a
  quieter topbar.
- The shell re-sizes every button in the page host, and a page-wide control rule
  outranks a plain class: a component's own controls have to declare their size
  at a specificity that wins, or they come back as strips inside their cards.
- The generic button texture has to keep excluding the primary classes  on every branch. Its attribute-selector branch carries enough specificity to beat
  the primary rule below it, so a new primary-shaped class belongs in both
  branches' exclusion lists, not only in the primary rule — otherwise that
  button reads as greyed-out text on a dark pill.
- `--wm-font` names a family the app ships, and that is what makes a text reading
  a reading. `src/main.tsx` imports `@fontsource-variable/geist` ahead of the
  layer files; named and not delivered, every machine rendered the app in its own
  fallback sans — 12.6% wider on the CI runner than on a Windows machine — so a
  walk holding a character count or a pixel of slack passed in one place and
  failed in the other, and the surfaces it names looked like layout bugs. A
  surface that needs a font adds the import, not the name.
  [Narrative](docs/SHELL_AND_FRAME.md)

## Discovery

- Every Discovery step body is one card language: the wizard panel, the brief
  question with its count on the title line, the tick cards, the pressed-choice
  rule and the expert capture count. A new step composes those rather than
  inventing a card, so a rep recognises the same page from step to step.
- The programme-audio route is one question holding both ends: values prefixed
  for where sound leaves the video path and values prefixed for where it must
  arrive, split by prefix in one derivation. One question, because a rep answers
  both ends in one conversation and two questions let the halves disagree.

## Video wall

- The guided wizard's first step leads with the LED brief — canvas pixels,
  pixel pitch and the cabinet array — with the common walls under them, because
  those three are the customer's facts and a preset already answers all three.
- Four surfaces name the wall workflow, so the entry's name and the sentence
  saying how a design begins live once, in `lib/wallEntry.ts`. They had drifted.
- The focused view starts from a wall, not a room: a starting point is a whole
  brief named for what the wall does, grouped by technology for the shared
  picker. A rep's own saved wall joins that picker, keyed by a stable hash of
  the brief with the survey fields stripped, so another room's measurements
  never ride along and re-saving a wall moves its row rather than duplicating it.
  The save and load paths run the same shape rule, or a wall's key would change
  between saving and the next visit.
- The picker narrows on the facts its rows print, and every chip value comes
  from the walls themselves so no chip is a dead end. A count is a floor rather
  than an equality — an exact match hides every other wall and leaves a rep
  looking at one — and the copy under the chips says so. The filter hides rows
  only: families keep their order and an empty result says so with its own way
  out.
- A design remembers the card it started on, written by the card pick and only
  by it, so a handoff, a shared link and a restart leave the design without one.
- The brief list has to reach the whole option catalogue, not just the popular
  walls, and a test fails when a catalogued option is nobody's recommendation.
  The field is always open under the verdict with a range key above the rows,
  because a rep is choosing between ranges before part numbers.
- A projection screen can be several projectors: the units sit side by side
  carrying one canvas, a slice each, and a measured overlap replaces the seam
  with the band the images share. The seam is the control for an unequal pair,
  with a floor under each image so one cannot vanish.
- The guided result is read one pass at a time: the order of the passes and
  the one-line status under each name are data, the screen renders only the
  selected pass, and the save actions belong to the pass that decides them. The
  pass on screen is view state in storage and in the address, so a reload and a
  copied link both reopen it, and a link's pass outranks the stored one.
- The address also names the wall and the rep's pick. The wall token is the
  brief — what the wall has to do — while the pick says which catalogue design
  was chosen, so a choice never rewrites the requirement it answers, and one
  helper composes the link from the three rules that own a half.
- A saved wall records its owner and its template, so a design can be traced
  back after a project is copied.
- The elevation stands the wall on its mounting height, and a composed window
  plan must not be mistaken for the wall's own tiling, so the array stays the
  drawing's subject and the window tint stays content.
- The transport plan is one rule for the drawing and the table: an over-limit
  run is marked where the cable lands and the table's status cell carries the
  fix, so a rep does not leave the design to make the design right.
- A hand-entered run is checked against that link's printed allowance before it
  lands, and the CSV import runs the same rule, holding the whole sheet when any
  run is far from its allowance rather than applying half a survey.
- A worksheet photo never changes the design by itself: every usable row is a
  reading with its own confidence and reader note, and only the ids a rep leaves
  accepted are applied. Confidence describes reading legibility, not transport
  risk. A batch names a failed photo without discarding the rest and unions the
  rows it could not read into one list to type.
- The verdict answers before it argues: the signal-path sentence sits under the
  summary of the design it recommends, the reasons are one column, and the
  checks worth confirming before ordering sit behind a details line with their
  count on it, because a rep reads the answer first.

## Proposal output

- `buildProposalHtml` is the only printed and PDF surface, so page setup,
  running headers and section order live there; the PDF export opens it and
  prints. An edit that reaches only a screen has not reached the document.
- Every proposal document names the product data it was read from: one line
  carrying the manifest digest, the manifest's assembly time and the build
  commit. The Word footer, the printed control block and the CRM payload read
  one record (`productDataRevision()`), so a document cannot quote a revision
  the send that carries it does not. The digest is over the manifest's content
  rather than its bytes — two checkouts of one commit disagree about line
  endings, and `generatedAt` is excluded from it for the same reason in
  miniature: the timestamp dates a run, the digest identifies the data. A
  missing value prints `unknown` or `unversioned` instead of a guess, and the
  commit carries `+dirty` when the tree it was built from was uncommitted,
  because a document naming a clean commit for uncommitted code is the failure
  this line exists to prevent. [Narrative](docs/PROPOSAL_OUTPUT.md)
- A document's detail level decides which sections print: every section is filed
  at the shallowest level that carries it, and the levels are a ladder whose cut
  is the document's own layers. A new section is filed once, not branched on.
- Proposal copy has two layers: authoring guidance the wizard seeds into a draft,
  and the customer layer that may print. Export builders read only the customer
  layer and run free text through the same filter, because a rep's note is not
  customer copy.
- An over-limit wall cable run and a surveyed run past the receiver's rating both
  hold the export, and each offers its own one-tap fix where the rep meets it —
  the template page applies the fix rather than describing it, and the project
  record offers the same fix because that is where a rep is reading.
- A governed dependency prompt holds the export too. Answering one records the
  decision on the stored project and leaves the prompt in the document's
  dependency list, where the question belongs, while the BOM drops it. Only
  prompts are ever dropped: a stored list naming an exact dependency takes no
  equipment out of the room.
- A template is a starting point for a different room, so a dependency prompt
  does not travel as scope and does not reach a template's export gate: one rule
  makes a new template out of a project, and every save path goes through it. A
  save is a projection, so the record it came from keeps its own response.
- The focused home has one primary action, and it is choosing a room template.
- The project record reviews requirements but does not edit them, because the
  record is what was captured and the wizard is where it changes.
- An unfinished wall survey is a completeness warning rather than a blocker, but
  it prints where the proposal is exported and can be cleared from there, so the
  warning and its way out sit together.
- The survey's per-link install detail is priced scope: the installation
  schedule reads it, and the Word export prints that priced table after the
  equipment table so the two read as one scope.
- Installation rates start from one saved rate card rather than from the last
  proposal, because a rate typed once should be reused and a rate typed into a
  document should not become the next document's price.
- Equipment pricing has one rule, and the printed schedules repeat their header
  on every page; Word rows go through one private row helper, and the Word
  export carries its own running header and footer rather than inheriting the
  screen's.
- A template-driven proposal is priced on the template review page, not in the
  proposal wizard, and that review is a staged pre-issue walk rather than one
  long page. The walk remembers where the rep left it.
- A template's copy carries the design, not the room it was measured in.
  [Narrative](docs/PROPOSAL_OUTPUT.md)

## Drawing symbols and stencils

- The Visio stencil is a real package, built from symbol data by a script, and
  what makes it a stencil rather than a drawing is one content-type string. That
  is asserted rather than restated, because copying content types from a drawing
  is the mistake that would leave Visio opening it as the wrong kind of file.
- Each symbol is one shape whose rows carry both a value and a formula, so a
  designer who resizes the dropped shape moves the drawing with it. The fields a
  rep fills in and the directionless glue points follow Visio's own equipment
  masters, and the pane icon is drawn from the same geometry, so a new symbol
  cannot arrive as a blank square.
- Nothing here can open the file, so the builder checks the class of defect Visio
  answers with a repair prompt — before writing, so a package that does not hold
  together is never produced. First use in Visio is the real test; quote any
  prompt back rather than assuming the package is right.
- The build is deterministic down to the byte, so rebuilding an unchanged symbol
  set produces an identical file and a diff means a symbol changed. A new symbol
  is one entry in the catalogue and nothing else. Do not add an npm script for
  it: `package.json` is an input to the browser walk's fresh-build gate, so a new
  script would refuse a build that is still current.
  [Narrative](docs/DRAWING_SYMBOLS.md)

## Compare feature

- `CompareConfidenceTier` is the single source of truth for verdict tone.
  Surfaces derive colour and emphasis from the chip's tone, never from the status
  class: a "pending" verdict pairs with a no-match status class but must stay
  amber, and the status class is about the outcome rather than about how much is
  known.
- The verdict-lead status class lives on the section and the banner is a child
  of it, so CSS matching both needs a descendant selector rather than a
  compound.
- Compare styling stays scoped to the compare route. The page entry is a route
  component over modules in `pages/compare/`, and the rule for that split is the
  proposal wizard's: pure logic leaves, React stays, and the candidate rules
  live in the engine's own modules rather than in the page.

## Backend API

- No-match is a business outcome, not a request error: the match routes answer
  200 with a failure envelope. The permission gate fires before any handler's
  status logic, so a handler change never affects the 401 contract.
- Dead routes stay protected by contract tests rather than deleted quietly, and
  the historical Express-style export is retired.
- The JSON body reader enforces its ceiling, and the CSRF double-submit guard is
  inert until its environment flag is set — so a CSRF test proves the guard, not
  the app.
- A development server holds a real workspace session instead of a browser-side
  stand-in: one endpoint creates a fixed local owner in the API's own store, so
  the pair can be driven without signing in on anyone's browser.
- The worksheet reader requires the printed rows as well as the image, so a
  transcription can only name links the design has; the client re-checks that
  and reports unread rows by id instead of clearing runs. The site-photo reader
  carries the same switch, and the mock is threaded into both reads, because a
  mock that answers one half reads as a real analysis of the other.
  [Narrative](docs/BACKEND_API.md)

## Project record and site survey

- A stale clean survey is renewed where it is flagged, and the Projects
  navigation entry carries the count of rooms that need survey attention, so a
  rep sees there is survey work before opening the list.
- The project page's address is one contract: the query names the section on
  screen and the hash names a panel inside it. One registry owns both halves, so
  a link builds its address from the registry instead of assembling its own.
- A survey's per-link install detail is free text keyed by transport link, and it
  round-trips through the CSV sheet and the photo scan, because enclosure, mount
  and termination are the rep's words rather than a taxonomy.
- The worksheet explains its own number columns, because the surveyor reads it
  with the builder closed.
